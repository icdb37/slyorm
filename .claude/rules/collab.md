# 协作规范（collab）

> 管理对象：讨论与实现的交互流程 —— 开放讨论怎么给答案、指定方案怎么执行、发现不可行时如何中断。
> 适用于全部会话，先于任何技术栈规范生效。
> 与代码层面的「不留过渡逻辑」要求互不冲突：那条约束**代码不留兼容尾巴**，本规范约束**不擅自替换用户指定的实现路径**。

## 一、开放讨论：给选项，不给单点答案

用户提出开放性问题或征求方案（「如何实现 X」「讨论一下」「怎么做好」）时：

- 给出 **2~4 个**候选方案 / 答案；问题本身只有唯一解时须说明为何唯一
- 每个方案一句话取舍，明确标注推荐项与理由
- 不在未获用户选定前按推荐项展开实现

> 本节只管答案形态；「什么时候动手」由 [chat.md](chat.md) 判定（询问类不动手、否定词优先）。

## 二、指定方案：先探索可行性，不擅自换方案

用户明确要求「按方案 X 实现」时：

1. 默认 X 可行：先深入探索 X 的**清晰、合理、简洁**实现路径（读代码、查依赖、必要时做小实验验证），再动手
2. 探索发现**硬性不可行**（语言 / 依赖 / 工具链层面的客观障碍，且有一手证据）→ **明确中断**，见 §三
3. X 可行但有代价（引依赖、改工具链、性能开销）→ 照常按 X 实现，代价如实报告；代价不构成换方案的理由

判定试金石：

| 情形 | 处置 |
|---|---|
| X 能实现，只是我觉得别处更优雅 | 按 X 实现 |
| X 能实现，但要引依赖 / 改构建链 | 按 X 实现 + 报告代价 |
| X 在当前语言 / 工具链下编译期或运行期必然失败（有证据） | 中断 + 证据 + 替代选项 |

## 三、中断的形态

「明确中断」不是换个说法继续干，而是把决策权交还用户：

- **结论先行**：此路不通，以及为什么
- **证据**：报错原文 / 最小实验 / 权威文档链接
- **出路**：2~4 个可选方向（回到 §一 的选项格式）
- 未获用户确认前，不落任何替代方案的代码

## 反例（❌）

- ❌ 用户要求 A，A 受阻后未加说明直接交付「B 也能达到目的」的实现 —— 静默换方案
- ❌ 把「方案有取舍 / 不够优雅」当成「不可行」，径自降级实现
- ❌ 浅尝辄止（没做实验、没查文档）就宣布不可行 —— 中断必须建立在深入探索的证据上
- ❌ 开放讨论只给单一方案，或给出多方案后不经确认就按推荐项开工
