# 代码注释规范（前后端通用）

> 核心理念：**准确、清晰、简洁、高可读性**
> 注释回答「为什么这样 + 功能概述」，不写「做什么」「怎么做」「外部章节引用」。
> 示例以 Go 为例；规范本体不含项目文件引用，可直接跨项目复用。项目落地基线按 §六 由各项目自维护。

---

## 一、总则

| 维度 | 注释责任 | 代码责任 |
|---|---|---|
| 做什么 | ❌ 不写 | ✅ 函数名/语句本身已说明 |
| 怎么做 | ❌ 不写 | ✅ 实现即答案（SQL/正则除外，见 §5.2） |
| **为什么这样** | ✅ 写 | — |
| **功能概述** | ✅ 写（存在业务限定时，见 §三） | — |
| 边界/不变量/约束 | ✅ 写 | `return error` 自然守门 |
| 外部章节引用（§/issue） | ❌ 不写 | — |

**单一信息源原则**：业务约束只在 `return error` 处表达；注释用「功能概述」传达语义，不复述代码、不指向外部章节。

**形式**：
- 一般注释统一用 `//` 单行形式（Go 无 `/* */` 块注释用法）
- ❌ 禁止**函数头多行模板式注释**（「概述 + 参数 + 约束罗列」的连续多行 `// ...`）—— AI 模板味的主要来源
- ✅ 两处例外：导出类型与数据结构（struct / 字段映射表）上的**单行** `//` 注释（置于字段正上方，驱动 IDE hover 提示）；`// Deprecated:`（godoc 协议，IDE/godoc 渲染删除线，见 §5.5）
- **Go 行业规范（Effective Go / CodeReviewComments）**：文档注释以被注释标识符命名开头（`// Xxx ...`，不要 `// This function ...`），godoc 协议要求
- **Go 行业规范（golint/revive）**：所有 exported 标识符（首字母大写）必须有文档注释——这是机器可执行的硬约束。规范 §三「按信号判断内容」与该硬约束并不冲突：doc comment 必写，但内容遵守简洁原则，不要堆砌模板

## 二、长度上限

| 类型 | 上限 | 说明 |
|---|---|---|
| 函数头注释 | **1 行为常态，5 行为上限** | 出现 8 行 = 坏味道信号：拆函数，或信息该下沉到代码 |
| 行内 `//` 注释 | **≤2 行** | 超出 → 抽函数或精简 |
| 文件/包头注释 | **1 句话**（包注释 ≤ 1 段） | 本文件职责一句话点题 |
| TODO 注释 | 1 行 | `[TODO #issue] 一句话` |

> 只数行数，不数字数 —— 可机械执行的标准才有约束力。
> 超出上限 = 信号：要么拆函数，要么该删注释（代码已自明）。

## 三、必写场景（信号触发，但 exported 必写）

1. **函数头注释**：
   - 所有 exported 标识符（首字母大写）必须有文档注释（golint/revive 硬约束）
   - 内容按「信号」判断：存在**非显然的业务限定或陷阱**（如「仅特定收款模式可结」「期初单不走红冲」）→ 必须点出
   - 函数名 + 参数/返回类型已自明且无业务陷阱 → 1 句话概述即可，不要堆砌模板（避免命中 §四 黑名单）
   - **判断标尺：合上注释读代码，会不会有某个 `if` 让人停下来问「为什么」？会，就在那儿写**
2. **行内注释**：仅在「非显然行为」「防御性校验存在理由」「关键不变量」「SQL/正则的业务口径」四处写
3. **包注释**：平铺目录时，在任一文件顶部以 `// Package <name> ...` 描述本包职责（典型为包名同名文件或 `doc.go`）；目录命名已承担职责时**不强制**，不为放一行注释新建 `doc.go`
4. **TODO**：未完成事项必须挂 issue 号；任务完成**立即删除** TODO 注释

## 四、不写场景（黑名单）

- ❌ 复述函数名（`// 创建订单`）—— 「必写」压力不是写废话的理由，没有可写的就不写
- ❌ 复述循环体（`// 遍历 items`）
- ❌ 函数头多行模板式注释 —— 统一用 `//`，内容不超过 5 行（struct 字段映射表上的单行注释与 `// Deprecated:` 除外，见 §一）
- ❌ 在注释重列参数类型（Go 类型签名已声明）
- ❌ 只提高音量、不携带信息的前缀（`注意：` `重要：` `关键：`）；携带理由类别的前缀（`防御：` `口径：` `不变量：`）可用
- ❌ 历史变更叙述（`// 之前是 XXX，改成 YYY` `// 修订：...`）—— git blame 干这事
- ❌ 外部章节引用（`需求单 §5.2` `设计文档 §6.2` `评审纪要 §10`）—— 用功能概述替代（TODO 的 issue 号是唯一例外，见 §5.4）
- ❌ 注释掉的代码块 —— git 找得回，直接删
- ❌ AI 生成的多行解释模板（`本函数用于...，具体实现...，注意...，总结...`）
- ❌ doc comment 不以被注释标识符名开头（`// 这个函数用于...`）—— 违反 Effective Go

## 五、各模块统一模板

### 5.1 函数头注释

```go
// Xxx 一句话功能概述；关键不变量或业务限定
func Xxx(...) (...) { ... }
```

**正例**（名称看不出业务限定，必写）：
```go
// VoidPayment 红冲留痕；期初单无来源单据，仅重算往来余额
func VoidPayment(...) error { ... }

// SettleOrderFreight 订单运费结算：仅承运方代收模式可结，且必须一次性结清
func SettleOrderFreight(...) error { ... }
```

**不写例**（名称 + 签名已自明，硬加注释只会命中黑名单第一条）：
```go
func UpdateOrder(ctx context.Context, p OrderUpdate) (OrderDetail, error) { ... }
```
> 仍需 1 句话 doc comment（exported 必写）：`// UpdateOrder 更新订单并返回最新详情`

**反例**：
```go
// 订单服务：状态机、成本快照、运费计入应收、收款边界、
// 作废前置校验与红冲。VO 由 dao 层装配，本层只做事务编排。
// ❌ 3 行 AI 模板味；首句「状态机、成本快照、...」是清单而非概述
// ❌ 函数名未作为注释开头（违反 Effective Go）
func OrderService(...) { ... }
```

### 5.2 行内 `//` 注释

**正例**：
```go
// 防御：待出库订单天然 shipped_quantity=0，但显式校验防状态机漂移
if hasShipped {
    return ErrOrderPartiallyShipped
}

// TO_CUSTOMER 应收含运费（客户货到付款）；TO_CARRIER 运费走独立结算不计入
total := freightPayeeTotal(order)
```

**SQL / 正则放宽**：这两类语句「实现即答案」失效（自明性最差），字段映射、业务口径、排序语义值得写：
```go
// 流水表字段映射（无 updated_at 列；append-only）
// 期间收支汇总（仅有效单据；作废单据的历史收款自动出统计）
```

**反例**：
```go
// 需求单 §5.2：结算只写账本附属行 + 订单结算列；
// 旧结算表已删
// ❌ 外部引用 + 历史清理叙述；「为什么」应是功能概述而非变更记录

// 注意：这里要校验金额
if amount <= 0 { return ErrInvalidAmount }
// ❌ 只提高音量没提供信息 + 复述代码
```

### 5.3 文件/包头注释

```go
// Package <name>：<职责一句话>        （尖括号为占位符）
```

如 `// Package payment：付款作废与红冲留痕；期初单仅重算往来余额`。放在包名同名文件或 `doc.go` 顶部，1 句话点题本包职责；目录命名已承担职责时不强制（见 §三.3）。

### 5.4 TODO 注释

```go
// [TODO #234] settleDate 改服务端时区口径，避免前端传值漂移
```

- 必须挂 issue 号；无 issue 的 TODO 不允许遗留
- 与 §四「禁外部引用」不矛盾：黑名单禁的是**长期存活的注释**指向会漂移的外部章节；TODO 是**临时物**，完成即整行删除，不存在双维护
- 任务完成**立即删除**整行 TODO 注释
- 详细上下文写在 issue 评论区，不在代码注释里展开

### 5.5 `// Deprecated:`（godoc 删除线标记的唯一豁免）

```go
// SettleFreightLegacy 旧运费结算入口；新代码请使用 SettleOrderFreight。
//
// Deprecated: 改用 SettleOrderFreight，2026-11 移除
func SettleFreightLegacy(...) error { ... }
```

IDE/godoc 按 `// Deprecated:` 协议渲染删除线警告，普通 `//` 没有这个能力；因此函数级注释中的「弃用」语义必须以 `// Deprecated:` 形式表达，单独段落（前置空行），置于功能概述之后。Go 行业规范要求 `D` 大写、`Deprecated:` 后接空格。

## 六、项目内 gold 基线（各项目自行维护）

规范本体不引用任何项目文件。每个项目落地时自选 2~3 条现役注释作为基线，记录在**项目侧**文件（命名如 `note.project.md`），并遵守：

- 引文直接**内嵌**，行号链接仅作辅助 —— 行号会漂移，内嵌引文才能自证
- 每条标注**核对日期**与状态：✅ 合规 / ⚠️ 待改（附合规改法）
- ⚠️ 条目修复后更新状态；相关代码重构后重新核对
- 基线文件跟随项目仓库，不随本规范迁移
- **未维护基线时按规范本体执行即可**，本节是可选项，不强制要求立项

## 七、改造案例（虚构示例）

演示「函数头模板 + 外部引用注释」的典型违规与修复。

### Before（反例，违反规范）

```go
// 订单结算—运费段。
// - 一次性结清；bill_no = 订单保存时投影的附属运费账单行号（需求单 §5.2）
// - freight_payee=TO_CUSTOMER 拒绝（客户货到付款，商家不参与）
// - 已结清拒绝
// - courier_id 必须与订单一致
func SettleOrderFreight(ctx context.Context) error { ... }

ts := now()
// 需求单 §5.2：结算只写账本附属行 + 订单结算列；旧结算表已删。
// 订单运费入账挪入同一事务（#10 原子性，评审 D6-1）。
err := db.Transaction(func(tx *sql.Tx) error { ... })
```

**违反点**：
- ❌ 函数头多行模板式注释（违反 §一形式规则）
- ❌ 5 行函数头（达到上限，且模板味重）
- ❌ 4 条业务约束与代码 `if` 链重复（双维护）
- ❌ 外部引用 `需求单 §5.2`、`#10 原子性`、`评审 D6-1`
- ❌ 历史变更叙述 `旧结算表已删`
- ❌ 函数头不以标识符名 `SettleOrderFreight` 开头（违反 Effective Go）

### After（合规）

```go
// SettleOrderFreight 订单运费结算：仅承运方代收可结且必须一次性结清，写账本运费行 + 订单结算列
func SettleOrderFreight(ctx context.Context) error { ... }

ts := now()
// 账本写入与订单结算列同事务原子提交
err := db.Transaction(func(tx *sql.Tx) error { ... })
```

**改造原则**：
1. 业务约束（一次性结清 / TO_CUSTOMER 拒绝 / 已结清拒绝 / courier 一致）已在代码 `if` + `return error` 链中表达，注释不复述
2. 外部引用、历史变更叙述一律删除，由代码当前状态自行说话
3. 函数头 1 句点出「仅承运方代收」这个业务关键限定，比 4 条罗列更有信号价值
4. 函数头以标识符名 `SettleOrderFreight` 开头（Effective Go 要求）
