# 文档管理规范（doc）

> 管理对象：`.claude/` 下全部 markdown（CLAUDE.md、rules/、skills/）。
> 本规范约束「文档怎么建、怎么改、废弃内容怎么清」；各业务规范（fe / se / note）的内容本体不在管辖内。
> 核心原则与 note.md 对代码注释的要求同构：**文档只回答「现在怎么做」，不回答「过去发生过什么」** —— 变更历史由 git 承载。

## 一、目录结构与职责

| 位置 | 职责 | 内容边界 |
|---|---|---|
| `CLAUDE.md` | 唯一入口索引 | 项目概述 + rules/、skills/ 登记表（一行一文件），不承载规则条文 |
| `rules/` | 跨层硬规范（权威层） | 每领域一个文件：`chat.md` 指令语义、`collab.md` 协作、`code.md` 编码、`note.md` 注释、`doc.md` 本文件 |
| `skills/<name>/SKILL.md` | 单层实操手册（按需加载层） | 围绕「写某一个具体文件」的展开：骨架、流水线、反例、自检 grep |

**双入口同构**：仓库根的 `AGENTS.md` 是 `.claude/CLAUDE.md` 的硬链接，`.agents/` 是指向 `.claude/` 的本地链接（均已 gitignore）。改动 `CLAUDE.md` 后必须确认两者仍同步（改写类操作会断开硬链接，需重建）。

**内容放哪的判定**：

- 跨多个层/域的硬约束 → `rules/`
- 「怎么写某一个文件」的操作手册 → `skills/`，触发条件写进 frontmatter
- 两句以内能说清、只服务单一文件的 → 直接写进对应 skill，不新建 rules 文件
- CLAUDE.md 只有索引 —— 规则条文写进 CLAUDE.md 即违规

## 二、新建文档

- rules 文件命名：小写单词（`collab` / `common` / `note` / `code-log` / `doc`），一个领域一个文件，不建子目录
- 项目 skill 目录命名：`code-<对象>`（如 `code-api`、`code-dbx`），一个 `SKILL.md` 撑起一个 skill，不建附属文件；第三方通用技能（如 `skill-creator`）原样放置，不受本条约束
- SKILL.md 必须带 frontmatter：`name` 同目录名；`description` 写**触发条件**（「当用户…时使用 —— 即使没明确说 X 也应触发」），不写内容摘要
- 语言与风格与现有文档一致：中文、表格优先、正反例成对、反例 `❌` 前缀
- 新文件建好后必须在 CLAUDE.md（rules 类与 skill 类均在登记表加行）登记；未登记的文件视为不存在

## 三、修改文档（权威与同步）

- **权威层级**：rules 是本体，skill 是实操展开；每个 skill 末尾必须声明「冲突时以 xx.md 为准」
- **单一信息源**：规则条文只在权威文档维护一份；skill 引用规则用「见 note.md §X」+ 示例，不整段复制条文 —— 复制即埋漂移点
- **改权威文档必须过同步清单**：通用动作是 grep 全 `.claude/` 对被改章节的引用（`§章节名`）逐一核对，删除展开文档中与新口径冲突的旧描述
- **事实性陈述以代码为准**：文档中描述代码现状的句子（「auth 中间件已注入 `req.ctx`」），代码演进后必须同步改写 —— 这是最高频的漂移源

## 四、废弃内容清理（核心）

代码中已删除的功能，相关文档内容按下表处置：

| 类别 | 判定特征 | 处置 |
|---|---|---|
| 变更 / 历史叙述 | 「XX 已废弃并入 YY」「历史上…」「旧的逐步迁」—— 只解释文档为什么长这样，不改变任何输出行为 | **删**。git history 承载变更史 |
| 现存状态描述 | 「过渡期双登记」—— 描述代码当前真实状态，有行动价值 | **留**。代码迁移完成后随实况更新 |
| 防御性检测器 | `grep xxx（应 0 命中）`—— 抓存量残留，成本一行 | 存量清空前**留**，注释去叙事化（写「应 0 命中」，不写「已废弃」）；存量清空、新代码稳定数轮后删 |
| 纠偏模型通用倾向的反例 | 禁 `enum` 关键字、禁多行 JSDoc、禁 `as any`—— 约束模型自发行为，与项目演进无关 | **永久留**。每次会话都有效 |

**判定试金石**（两问）：

1. 这条内容约束的是「模型会自发想做的事」，还是「只有老代码才会出现的事」？前者永留，后者随存量清空而删。
2. 它还能改变模型当前的输出行为吗？不能 = 删。

**删除动作**：清理一个废弃符号时，全目录 grep 该符号，把叙事、示例、检测器、反例表四处一并对齐；只清一处会留下「半死」状态（符号仍被别处引用，比不清更糟）。

## 五、检测器（grep 抓手）质量门槛

任何 grep 检测器写入文档前，必须在真实代码上跑一遍并确认：

1. 方向正确：查「未做 X」的 grep 不能匹配「做了 X」的行
2. 不恒空：管道后接 `grep -v` 时，注意把命中全部排除的写法（输出恒空 = 形同虚设）
3. 占位符不能当字面量：`grep -v 'type Xxx'` 匹配不了 `type UserRole`，须改为「列出候选 + 逐个核对」两步法
4. 不做存在性误判：「任一处命中即整体通过」的管道无效；逐方法/逐文件判定须两步法（先列定义，再逐个核对）
5. 需人工甄别的必须写判定规则（何时违规、何时合规）
6. 本仓 grep 为 ugrep：以 `/` 开头的模式会被特殊解析，须加 `--` 分隔符；过滤注释写 `[/][/]`，直接写 `//` 作 `-v` 模式会吞掉全部输出（检测器静默失效）
7. `^` 锚定对 `grep -rn` 的输出永远无效（行首是 `路径:行号:` 前缀），要锚定行内容须把前缀算进模式

## 六、示例代码门槛

- 文档内示例必须能过项目 typecheck（字段名、方法签名、import 与代码一致）—— 模型模仿示例的倾向强于遵守文字规则
- 示例不得与同文档规约矛盾（规约说可选、示例写成必填 = 必有一处被违反）
- 描述代码现状的示例，代码变更后同步改

## 七、本文件自律

- 本规范自身适用 §四：不保留修订记录，变更说明写在 commit message
- 违反本规范的存量文档，发现即在当次相关修改中顺手修正，不单独立项
