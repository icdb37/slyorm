# 交互习惯（chat）

> 管理对象：**单条指令的语义判定** —— 本轮只答，还是动手（改代码 / 执行变更类操作）。
> 与 [collab.md](collab.md) 的分工：本文定「什么时候动手」，collab.md 定「动手或回答时给什么、怎么给」。

## 一、判定优先级

自上而下命中即停，否定压倒一切：

| 序 | 命中条件 | 模式 | 本轮动作 |
|---|---|---|---|
| 1 | 出现否定修改词（不要修改代码 / 只给答案 / 别动代码 / 仅分析） | 否定模式 | 只答，零写入 |
| 2 | 出现命令词（实现…功能 / 执行… / 新增… / 改一下… / 加个…） | 命令模式 | 直接动手：改代码或执行变更类操作 |
| 3 | 出现询问词（讨论一下 / 问一下 / 请问 / 如何 / 怎么 / 是不是） | 讨论模式 | 给方案与建议，不改代码 |
| 4 | 以上皆无 | 讨论模式（默认） | 同上，并回问是否需要落地实现 |

判定按**语义**而非字面：句中同时出现询问词与命令词时，看用户要求的**产出物**是答案还是改动。

## 二、三种模式

### 2.1 讨论模式（只答不改）

- **可做**：读代码、检索、翻历史、跑只读探查与测试，为答案取证。
- **产出**：结论先行；开放性问题给 2~4 个方案 + 每个一句话取舍 + 标注推荐项，唯一解时说明为何唯一（详见 [collab.md §一](collab.md)）；封闭型 / 审查型问题直接给结论与依据，不凑方案。
- **禁止**：新建 / 修改 / 删除仓库内文件，执行迁移、改配置、启动服务、提交代码。
- **交付**：同轮给全，不留到下一轮；用户选定前不按推荐项开工。

### 2.2 命令模式（直接动手）

- **可做**：直接动手 —— 修改代码，以及执行有副作用的操作（迁移、改配置、启动服务、提交代码）。
- **先规划后动手**：修改代码前先给规划与执行清单（改哪些文件、分几步、每步做什么），随即按清单逐项修改，同轮交付，不等确认。
- **需求本身开放式时**：按最贴合现有代码的一条路径实现，事后在回复里说明取舍；除非存在需要用户拍板的业务分支（是否引入新依赖、是否改表结构），否则不回问。
- **走既有流程**：新增特性按 [skills/code-flow](../skills/code-flow/SKILL.md)；命名与注释按 [skills/code-name](../skills/code-name/SKILL.md)；数据访问按 [skills/code-dbx](../skills/code-dbx/SKILL.md)。
- **不可行时**：按 [collab.md §三](collab.md) 中断 —— 结论先行 + 一手证据 + 2~4 个出路，未获确认前不落替代方案的代码。

### 2.3 否定模式（只答不改，且以否定为准）

- 行为约束等同讨论模式，且**零写入**是硬约束。
- 同句既含命令词又含否定词（如「实现导出功能，不要修改代码」）：**按否定执行**，并在回复首句点出这处冲突，把决定权交回用户。

## 三、触发词对照

| 用户表述 | 模式 | 说明 |
|---|---|---|
| 「讨论一下订单状态机怎么设计」 | 讨论 | 询问词 → 给多方案 |
| 「问一下这个报错怎么处理」 | 讨论 | 询问词 → 给排查路径 |
| 「实现订单导出功能」 | 命令 | 命令词 → 动手 |
| 「执行一下数据库迁移」 | 命令 | 命令词 → 动手 |
| 「不要修改代码，只给方案」 | 否定 | 零写入 |
| 「先别动代码，看看这个函数怎么优化」 | 否定 | 零写入 |
| 「改一下这个 handler」 | 命令 | 命令词 → 动手 |
| 「这个写法对吗？」 | 讨论 | 审查型问题 |
| 「按方案 B 实现」 | 命令 | 指定方案 → 不擅改（collab §二） |

## 四、边界情形

| 情形 | 处置 |
|---|---|
| 「讨论下 X 怎么实现，实现完告诉我」 | 混合指令：产出物含「实现」→ 命令模式；其中方案选择若代价差异大，先给选项待确认 |
| 命令模式执行中，用户改口「等一下，不要改了」 | 立即停止写入，汇报已改动文件（清单 + 位置），是否回滚由用户决定 |
| 否定模式下被要求「跑一下看看」 | 只执行只读探查；会产生副作用的操作（迁移、启动服务、提交）仍不做 |
| 无法判断用户是否要改动 | 默认只答，并回问一句是否需要落地实现 |
| 讨论中用户改主意要实现 | 转命令模式，按命令模式执行 |

## 五、反例

- ❌ 用户问「讨论一下订单状态机怎么设计」，直接开写代码 —— 询问词 ≠ 命令词
- ❌ 用户说「实现订单导出功能」，先反问「要我怎么做」 —— 命令模式不需确认
- ❌ 列完执行清单就停下等确认才动手 —— 清单是先行交代，不是新增的确认关卡
- ❌ 用户说「不要修改代码，看看这个函数怎么优化」，顺手把函数重命名了 —— 否定是零写入硬约束
- ❌ 「实现 X 功能，不要修改代码」自相矛盾时自行挑一边执行 —— 必须按否定执行并点出冲突
- ❌ 讨论模式里为了「验证方案」顺手写了测试文件 —— 探查只读，验证需先确认
